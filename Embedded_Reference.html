CWE-347
CRC is not verification. An unkeyed linear code detects noise, not an adversary — anyone editing the image recomputes it. Signature over a hash is the authenticity decision; CRC is at most a fast-fail pre-check. This holds on every platform, which is why it is in the generic core and not an overlay.

AMD
It is an MPSoC, not an MCU. The KV260 carries a K26 SOM with a custom Zynq UltraScale+ device: quad Cortex-A53 APU, dual Cortex-R5F RPU, PMU, CSU, programmable logic, 4 GB DDR4. Calling it an MCU in an interview signals you have not used one — the distinguishing features are an MMU, external DRAM, multiple privilege levels including a secure world, and hardware isolation enforced at the interconnect rather than in the core. The "with encryption" SKU is the one where the CSU crypto path is usable: AES-GCM-256, RSA, SHA-3/384. That variant is also the one that carries export restrictions — know the ECCN conversation before an interview asks.

1.01 Qualifiers that mean something

CWE-14MSC06-C
volatile — every access is emitted, in order, never cached in a register. Correct uses: memory-mapped I/O, objects shared with an interrupt handler, setjmp locals. It is not atomicity, not a barrier against normal memory, not thread safety. The compiler deletes memset(key,0,n) at end of scope as a dead store. The key survives in RAM and in the stack frame the next call reuses. Zeroize through a volatile-qualified pointer or a barrier the optimizer cannot see through, then confirm in the disassembly rather than the source.
CWE-1232
Ordering is a separate problem. The compiler orders volatile accesses relative to each other; the processor and the interconnect do not order them relative to normal memory. Every architecture gives you barriers for this and every architecture has developers who skip them. Barrier after configuration writes that change how subsequent accesses are interpreted, before an effect must be globally visible, and after anything that changes memory attributes or the exception vector base.
CWE-321MISRA 8.13
const is a compile-time promise, not memory protection. Without a hardware region marking the range read-only, a wild pointer writes it. A key declared static const uint8_t root_key[16] is plaintext in the image. One flash dump, or strings on the shipped binary, and every unit that ever shipped is compromised at once.
CWE-663
static — internal linkage shrinks the symbol surface; block-scope static creates hidden shared state. A static scratch buffer in a parser is a data race waiting for a second caller, and a race in a parser is usually a write primitive.

1.02 Pointers, arrays, and precedence

CWE-467
Arrays decay at every call boundary, so sizeof in the callee measures a pointer. The canonical embedded overflow: a length that came from the wire, or a sizeof that measured four bytes instead of the buffer. Length travels beside every pointer. In C++, std::span carries the extent for you.
MISRA 12.1
*p++ vs (*p)++ vs *++p — postfix binds tighter than unary dereference.
*p++value at old p; p advances afterward
(*p)++value at *p; the pointee increments, p unchanged
*++pp advances first; value at the new target
The expression's value is the answer, not where the pointer ends up. Reading these as "where does p point now" is what produced the last stack overflow under ASan.
CWE-823ARR30-C
Pointer arithmetic is defined only inside the object and one past its end. Forming an out-of-range pointer is undefined before you dereference, which is why if (p + n > end) can be optimized away entirely. Bound with the offset: if (n > (size_t)(end - p)).
CWE-1189
Function pointers and vtables are the same primitive with different bookkeeping. A dispatch table in writable memory is a control-flow hijack target one out-of-bounds write away. Keep tables const so they land in read-only storage, cover that storage with a hardware read-only region, and index only with a validated enum.

1.03 Layout, padding, and what leaks

CWE-226CWE-200
Struct padding is uninitialized and the compiler never has to fill it. Serializing a struct with memcpy puts those bytes on the wire — whatever the stack last held, including key schedule fragments and pointers that defeat address-space randomization on the Linux side. Never cast a struct onto the wire, never memcmp two structs. Serialize field by field with explicit byte order.
MISRA 11.3
Packed structs remove padding and create unaligned members. Some access classes fault on unaligned addresses, and device-memory mappings almost always do. Casting a receive buffer to a packet struct is an alignment bug and a type-punning bug at once, and it hands the parser a length nobody validated.
CWE-190CWE-195
Integer promotion and conversion — a signed length compared against an unsigned size converts the wrong way, and a negative length becomes an enormous positive one at the memcpy boundary. Length types are fixed-width unsigned end to end. -Wconversion -Wsign-conversion plus MISRA essential-type rules catch what review misses.
Protocol
Endianness — both of your targets are little-endian; every wire format worth having is big-endian by declaration. Build counters into nonces with shift and mask, never a cast. An endianness bug in nonce construction is silent until two nodes disagree and collide.

1.05 Image layout and the pre-main window

Generic
Sections — code and constants in non-volatile storage, initialized data copied to RAM, zero-initialized data cleared, and some region deliberately left untouched. Every toolchain names these differently; the security questions are identical: what is writable, what is executable, and who decided. Read the map file every build. A section that moved is a memory-safety change nobody reviewed.
CWE-1189
W^X — no region is both writable and executable. This is free on both targets and is the single highest-value memory-protection decision you will make.
STM32F767ZI
CWE-121
Reset_Handler loads SP from vector[0], copies .data, zeroes .bss, runs SystemInit and static constructors, then main. Zeroize keys at the very top of it. PROVIDE region boundaries in the linker script and consume those symbols in MPU setup so protection cannot drift from layout. Reserve an explicit stack-guard region and give it a no-access region — deterministic, unlike watermark checking which only notices afterward.
Zynq UltraScale+ / K26
bootgen
There is no single image. A boot image is a container described by a BIF file and assembled by bootgen: FSBL, PMU firmware, ARM Trusted Firmware, U-Boot, the PL bitstream, R5 firmware, Linux. Each partition has its own destination processor, its own signing key, and its own load address. Treat the BIF as a security artifact under review. It is where authentication is enabled or quietly left off per partition, and a single unauthenticated partition breaks the chain no matter how good the others are.
CWE-1188
DDR is initialized by software, which means there is a window where the memory controller and its scrubbing are not yet configured. Anything staged before that window lives in OCM.

1.07 Caches, coherency, and shared buffers

Generic
The rule never changes. Clean before a non-coherent agent reads your buffer; invalidate after it writes one. Cache maintenance operates on whole lines, so a shared buffer that straddles a line with unrelated data will corrupt or resurrect that data. Align shared buffers to the cache line and round the length up to a multiple of it. Both targets punish you for skipping this, in ways that look like random corruption.
CWE-1421
Cache as a side channel — data-dependent memory access leaks through timing. Table-driven ciphers are the textbook case, and the mitigation is the same everywhere: uncached working memory, or a primitive with no secret-dependent lookups.
STM32F767ZI
Cortex-M7
16 KB I-cache + 16 KB D-cache, write-back, 32-byte lines. Clean before DMA transmit, invalidate after DMA receive, align DMA buffers to 32 bytes. Crypto working set in DTCM sidesteps the whole problem — uncached and constant-latency.
Zynq UltraScale+
CCI / ACP
Three classes of port and the choice is a security decision as much as a performance one: coherent ports where the interconnect maintains coherency for you, accelerator-coherent ports into the A53 cluster's caches, and high-performance ports with no coherency at all where software must maintain it. A PL accelerator on a non-coherent port reading a buffer the A53 has not cleaned sees stale data — and in the other direction, writes plaintext into a line the core later evicts over something else. Shared ring buffers between A53 and R5F go in uncached memory or get explicit maintenance on both sides. The intermittent-corruption bug you will spend a week on is always this.

1.09 Interview drill — Sheet 1

  1. Where does the key live at reset, and why there? Generic answer: memory no other bus master can reach, uncached, on-die, cleared in the first code after reset. On the F767 that is DTCM, covered by a privileged MPU region.On the MPSoC that is OCM or R5F TCM behind an XMPU region naming a single master ID — never DDR, which is off-chip and cold-boot exposed.
  2. Your MPU marks SRAM execute-never and the device faults immediately. First suspect? Something legitimately executes from RAM — a RAM-resident flash routine or an RTOS trampoline. Second suspect: a region base not aligned to its size, covering a range you did not intend.
  3. Explain why an MPU is weaker than an interconnect firewall. The MPU checks transactions issued by its own core. Every other master — DMA, an accelerator in the fabric, another cluster — is unchecked. An interconnect firewall checks at the slave by master ID, so it covers all of them.
  4. You must send a struct over a link. What do you do and why? Serialize field by field with explicit byte order. A raw copy ships uninitialized padding, which is an information disclosure of whatever the stack last held.

generic core + overlay

2.01 Task model — scheduling is a security decision

Generic
States — ready, running, blocked on an event with a deadline, suspended on nothing. The distinction that matters: a blocked task has a timeout and something eventually notices; a suspended task has neither.
CWE-323
Priority is a security parameter. Assign it from deadlines, then re-examine it from the attacker's side. Starve the key-rotation path and the session outlives its key lifetime. Starve it under a flood and the packet counter wraps under an unchanged key — nonce reuse, which in any AEAD means recovered keystream and forgeable tags. Rotation is high priority and short. Counter exhaustion is a hard stop that halts transmission, not a log line.
CWE-400
Bounded queues, bounded waits. Never block forever on a path an attacker can drive. Unbounded receive enqueue is a remote denial of service: flood the input, fill the queue, and legitimate traffic is dropped while the verifier drowns in forgeries. Cheapest rejection first — length and replay window before you spend a tag verification.

2.02 Synchronization and the inversion family

CWE-667
Mutex ≠ binary semaphore. A mutex has an owner and can therefore implement priority inheritance. A semaphore has no owner and cannot. Guard a resource with a binary semaphore and a low-priority holder is preempted indefinitely by mid-priority work while the high-priority security task waits. Unbounded priority inversion — the Mars Pathfinder failure, still shipping in new code.
RMA
Inversion → inheritance → ceiling. Inheritance boosts the holder for the duration of the wait. Immediate ceiling raises on acquisition to the highest priority of any task that can take the lock: bounded blocking, no deadlock, easier worst-case analysis, coarser in practice. Know the ceiling protocol by name and be able to say why you did not need it. That is the follow-up question.
CWE-833
Deadlock needs mutual exclusion, hold-and-wait, no preemption, and circular wait. Break the cycle with a documented global lock order. A deadlock reachable from network input is a remotely triggerable hang, and the watchdog reset that follows is the payload.

The doorbell is part of the attack surface, not plumbing.

2.04 R5F bare-metal vs A53 Linux vs the split — the tradeoff

You have not committed, and you should not until you know which of the two jobs this board is doing. The honest framing is that these are not three options; they are two roles and a decision about whether you need both.

Recommendation
The split is the defensible default — security-critical state and hard deadlines on the R5F, everything rich and untrusted on the A53, the boundary enforced by XMPU and XPPU rather than by convention, and the two talking over a narrow, validated message interface. Decide it when you know whether the board needs a network stack and a filesystem. If it does not, the R5-only posture is smaller, faster to verify, and honest. Do not adopt Linux because it is comfortable.
CWE-1189
If you take the split, the IPC boundary is the product. Shared ring buffers in reserved uncached memory, a doorbell interrupt, and a message format that the R5 side treats as fully hostile — length-checked, bounds-checked, no pointers, no structs cast onto the buffer. The tempting mistake is to trust Linux because you wrote both sides. The whole point of the split is that one side is expected to fall.

2.05 Watchdogs and failing secure

Generic
A hardware watchdog is only useful if petting it proves liveness. A single spinning task that keeps kicking the timer keeps a dead system looking alive. One software supervisor requires every registered task to check in within its own deadline, and only then pets the hardware. Windowed watchdogs, where kicking too early also faults, catch the runaway loop that happens to contain the kick.
CWE-636
Fail-safe versus fail-secure — safe means keep operating degraded; secure means stop rather than operate unauthenticated. On a defense program you will be asked which this subsystem is, and the answer is a requirement, not a preference. Write it into the threat model: repeated authentication failure stops the link. It does not fall back to plaintext.
V&V
Prove it trips. A watchdog that has never fired in test is an untested path in your most safety-relevant function. Block a task deliberately, confirm the reset, confirm the reset cause is readable afterward, confirm the post-reset path zeroizes keys first.
STM32F767ZI
RM0410
Independent watchdog runs from the low-speed internal oscillator, survives a main-clock or PLL failure, and cannot be stopped once started. Windowed watchdog adds the too-early check. Reset cause is readable from the clock-control status register — read it and act on it.
Zynq UltraScale+
PMU
System watchdog timers in both the low-power and full-power domains, plus a platform management unit that owns error management and can take a configured response — reset a subsystem rather than the whole device. Two things the MCU cannot do: run the R5 pair in lockstep so a divergence is detected in hardware, and reset the Linux domain without disturbing the real-time domain. Both are strong answers to "how does your system degrade." Linux adds its own layer — a userspace supervisor feeding the hardware watchdog. Same trap as the MCU: make it prove liveness of the things that matter, not of itself.

2.06 Entropy and random number generation

CWE-330SP 800-90B
Raw entropy is not a random number. A hardware source feeds a deterministic generator; the source needs continuous health tests — repetition count and adaptive proportion — with a hard failure path, not a warning. Cold boot before entropy accumulates, or a glitched source returning a stuck value, and the session nonce or ephemeral key is predictable. A tick-seeded or library rand() is the same failure with no excuse. Check the source's error flags on every draw, discard the first samples after enable, and never hand raw source output to a key derivation.
STM32F767ZI
TRNG
One true random number generator, and it is the whole entropy story on this part. Honor the seed-error and clock-error flags, discard the first sample, feed a software deterministic generator rather than using output directly as key material.
Zynq UltraScale+ / K26
CSU / TPM
Three independent sources here, which is a genuine advantage: the security unit's own generator, the A53 cryptography extensions for the primitives themselves, and the on-module TPM 2.0. On Linux, do not fight the kernel's entropy pool — feed it. The interesting design question is early boot, before any pool is seeded, which is exactly when the boot chain wants keys. Answer with a hardware source and a physically unclonable function, not with stored entropy.

2.07 Driver contracts and untrusted hardware

CWE-1284CWE-787
Hardware-reported lengths are input, not truth. Worked example from your radio: the nRF24L01+ product specification states that if the dynamic payload width reads above 32, the data is corrupt and the receive FIFO must be flushed. Trust it and copy that width into a 32-byte buffer, and the peripheral itself hands you a stack overflow — no attacker sophistication needed, just interference. Bound it, flush on violation, count the event. This is your best answer when an interviewer asks for a time you validated data from hardware, and the principle generalizes to every descriptor, every length field, and every status register on either platform.
MISRA 17.7
Layering exists to name the trust boundary. Everything below the parser is untrusted input; everything above is validated. Functions on that boundary get explicit pre- and postcondition comments, validate inputs, and return a status the caller checks.
CWE-134MISRA 21.6
Instrumentation — formatted printing over a serial port perturbs timing enough to hide the bug, drags in a heap and a format parser, and is a format-string surface. Use a low-overhead trace channel and a logic analyzer for ground truth. Never log key material or plaintext. A debug build that leaks the session key is a key disclosure with extra steps.
Radio
The radio's integrity features are not security. An unkeyed CRC, an address filter, and automatic retransmit are all reproducible by anyone with a second module. The address is transmitted in the clear and is a filter, not authentication. Everything above the link treats a received frame as fully attacker-controlled. The authenticated-encryption tag is the only thing that grants trust.

2.08 Interview drill — Sheet 2

  1. Which of your synchronization objects are exposed to unbounded priority inversion? Every binary or counting semaphore used for mutual exclusion. Mutexes have an owner so inheritance can apply; semaphores have nobody to boost.
  2. Your counter is four bytes. What is the failure at wrap, and what happens if a brownout loses it? Wrap under an unchanged key is nonce reuse: keystream recovery and forgeable tags. Brownout is the harder version — persist ahead of use with margin, or force a rekey on every reset, which is simpler and defensible.
  3. Why is a DMA-capable driver a bigger problem than a polled one? The DMA engine acts with full bus privilege on an address your driver supplied. On a core-MPU part nothing checks it but your code.On this MPSoC the XMPU checks it at the slave by master ID, which is the concrete reason interconnect isolation beats a core MPU.
  4. Justify your R5F versus A53 partitioning to a program lead. Security-critical state and hard deadlines on the R5F where the surface is small and the evidence is tractable; rich services on the A53; the boundary enforced by XMPU and XPPU, not convention; a narrow validated message interface between them, with the R5 side treating Linux as already compromised.
  5. The peripheral reports a payload larger than the buffer. What does your driver do? Reject, flush, count, and carry on. Trusting a hardware-supplied length is a buffer overflow you were handed for free.

3.01 Chain of trust — the generic model

Each stage verifies the next before transferring control. The chain is worth exactly as much as its first link, and the first link must be something the attacker cannot rewrite.

RootImmutable code, plus a public key or its hash in one-way storage

CWE-1326SP 800-193
Secure boot and measured boot answer different questions. Secure boot refuses to run code that fails verification. Measured boot runs it but records what ran into a tamper-evident log, so a remote party can decide whether to trust the result. They compose: verify locally, attest remotely. Know the triad from the platform-resiliency guidance — protect, detect, recover. A design that only protects has no answer for the day protection fails.
CWE-494
Anti-rollback is separate from signature verification. An attacker replays a genuinely signed old image carrying a patched vulnerability. Every signature checks out. This is why authenticity alone is not enough. One-way version storage, checked before handoff, unreachable from the application. A counter in ordinary writable storage is a counter the attacker resets.
CWE-367CWE-1247
Verify-then-execute is a race. Anything that can modify the image between the check and the jump defeats it, and a voltage or clock glitch at the verify branch skips the check outright. Write-protect what you verified, keep the window minimal, and make the decision hard to glitch — redundant checks with differing encodings rather than one branch on a boolean.

3.02 Chain of trust on an MCU with no boot ROM verification

CWE-1326
Real answer versus textbook answer. The textbook says the root of trust is immutable hardware. This part has no ROM that verifies your code, so the honest answer is a first-stage bootloader in the lowest flash sectors made practically immutable by write protection plus readout protection — weaker than a hardware root, and you should say so. Naming the limit of your own design is what separates candidates. Point at ST's secure boot and firmware update reference implementation as the design you compared against.
Option bytes
The controls you actually have — boot address option bytes select the entry point; write protection locks the bootloader sectors; proprietary code readout protection can make a region execute-only; the one-time-programmable area holds a public key hash and rollback bits; the dual-bank option enables read-while-write for A/B update. Burn one one-time bit per accepted version. Stage into the inactive bank, verify, swap, and let the new image set a confirmation flag only after it passes self-test — an unconfirmed boot reverts.
CWE-1329
The vendor system bootloader is a door you did not install. With the boot pin asserted the part enters a ROM loader that speaks serial protocols and will read and write flash for whoever holds the pin. Tie the pin low in hardware and set boot address option bytes deliberately. The highest readout-protection level also closes this path, which is one of its main jobs.

3.03 Chain of trust with a real hardware root

UG1085
The sequence. On release from reset the platform management unit runs its boot ROM and brings up the configuration and security unit. The CSU boot ROM — running on a triple-redundant secure processor with its own ROM and private RAM — reads the boot mode, authenticates and optionally decrypts the first-stage bootloader, establishes the root of trust, locks the boot security resources, and hands the chain to the FSBL on either the APU or the RPU. The FSBL then loads platform management firmware, ARM Trusted Firmware, the bitstream, U-Boot, R5 firmware, and Linux, verifying each partition as it goes. Boot security here is largely orthogonal to TrustZone. They are separate mechanisms that people conflate constantly — a good thing to get right out loud.
CSU
The crypto you get. AES-GCM-256, RSA, SHA-3/384, and a random number generator, all in the security unit's crypto interface block, and all still available at runtime after boot. The unit also performs tamper response monitoring once the system is up. This is the "with encryption" SKU's entire value. Without it the chain of trust is a paper design.
eFUSE
The fuses that matter. RSA_EN forces every boot to be authenticated. JTAG_DIS disables the debug interface. Alongside them sit the primary public key hash, secondary key identifiers used for revocation, and the device AES key. Two-tier key structure: the primary key is fused and permanent; secondary keys sign partitions and are revocable by identifier. That is how you rotate a signing key without bricking fielded units, and it is a question a hiring panel will ask. Fuses are one-way. Blowing JTAG_DIS or the highest security fuses on your only board ends your ability to debug it, permanently. Practise the sequence in emulation and on a sacrificial unit first.
CWE-1300
Key storage, three ways. Fused key: permanent, no battery, no rotation. Battery-backed RAM: rotatable and erasable on tamper, but needs a battery. Physically-unclonable-function-wrapped: the key is derived from device physics and stored only in encrypted form, so nothing at rest is the key. Key rolling — encrypting different partitions under different derived keys — exists specifically to limit differential power analysis exposure. Naming that as a countermeasure rather than a performance feature shows you know what side channels are. The security unit locks the protected AES key out as a runtime source when the first-stage bootloader is not itself encrypted. Confidentiality of protected partitions survives even if authentication is later distrusted.
TPM 2.0
Measured boot on the module. The K26 carries an Infineon TPM 2.0 alongside the MPSoC root of trust, giving you measurement, remote attestation, and sealed storage. Secure boot is local refusal; the TPM is how a remote party gets evidence. On a fielded defense system the second one is often the requirement that actually appears in the specification.
CNSA 2.0
The forward-looking gap, and it is interview gold. The immutable boot ROM authenticates with RSA-4096. NSA's Commercial National Security Algorithm Suite 2.0 requires quantum-resistant signatures for firmware and software signing, and RSA is not one. The ROM cannot be changed. The mitigation pattern is layered: keep vendor secure boot enabled, encrypt the first stage with the device key, keep that stage minimal, and have it verify all operational firmware with a post-quantum signature scheme before execution. Third-party boot loaders exist that do exactly this. Raising this unprompted in a defense interview is a strong signal — it shows you track the standards timeline, not just the datasheet.

3.04 Privilege model and core security state

Generic
Isolation needs two things — a privilege boundary that code cannot cross by choice, and a gate through which it can be crossed on request. Without both, memory protection is decoration: regions marked unprivileged mean nothing if everything runs privileged.
CWE-1189
The exception vector base is a hijack target on any architecture that lets you relocate it into writable memory. Keep it in read-only storage, or protect and periodically re-verify the copy.
STM32F767ZI · ARMv7-M
CONTROL
Thread mode can be unprivileged on the process stack; handlers are always privileged on the main stack; entry to the kernel goes through a supervisor call. Vector table base stays in flash. Deferred floating-point stacking leaves one task's registers live for the next. If a secret ever touches a floating-point register, disable it. There is no TrustZone on Cortex-M7 — that is an ARMv8-M feature. Claiming otherwise in an interview is an instant credibility loss.
Zynq UltraScale+ · ARMv8-A
EL0–EL3
Four exception levels: applications, kernel, hypervisor, and secure monitor — with ARM Trusted Firmware occupying the monitor level and mediating between the normal and secure worlds. The R5F cluster sits outside that hierarchy with its own protection unit and, optionally, lockstep execution. Map it out loud: unprivileged application, kernel, optional hypervisor for domain separation, secure monitor holding the crown jewels, and a real-time cluster the rich side cannot reach because the interconnect refuses its transactions. That paragraph is the answer to half the architecture questions you will get.

3.05 Debug interfaces and readout

CWE-1191
An open debug port is the shortest path to everything. It is the most common finding in embedded assessments and the easiest to fix late and forget. Close it for anything fielded, and understand the trade you are making: no failure analysis on returned units. Be able to argue both sides — that is a systems-engineering question wearing security clothes.
STM32F767ZI
RDP
Three readout-protection levels: open, flash unreadable while debug is attached with a mass erase on regression, and permanent disablement of debug and the system bootloader. Layer write protection over the bootloader sectors and execute-only protection over sensitive code. Published research has broken readout protection on several families of this vendor's parts using voltage glitching and debug stepping. Defense in depth, never the sole reason a secret is safe.
Zynq UltraScale+
eFUSE
A fuse disables the debug interface outright, and the debug access port can be restricted rather than killed — an authenticated debug path exists, where a signed challenge re-opens access for an authorized party. Authenticated debug is the grown-up answer to the failure-analysis trade the MCU forces on you. If you can only remember one differentiator here, remember that one.

3.06 Cryptographic engineering

CWE-323
Nonce discipline is the whole security budget of an authenticated-encryption construction. Counter plus per-direction salt, never repeating under a key, with a persistence story that survives power loss. Persist ahead of use with margin, or force a rekey on every reset. The second is simpler and easier to defend.
CWE-208
Tag comparison is never a byte-by-byte compare. Accumulate the difference across all bytes, branch once on the accumulator. Early exit leaks the count of matching leading bytes, turning an infeasible forgery search into a byte-at-a-time walk. Truncating a tag to fit a payload budget is a deliberate trade — document the per-attempt forgery probability, rate-limit failures, and count them.
FIPS 140-3SP 800-88
Zeroization is testable. On session end, tamper, fault, and reset the key leaves memory — the arena, the stack frames the crypto ran in, and any staging buffer a peripheral could see. Audit it by halting after teardown and searching memory for the key bytes. If you find them, the feature is not done.
STM32F767ZI
SP 800-232
No accelerator, so everything is software and the choice is about side-channel posture and code size. Ascon-AEAD128 is table-free, which removes the cache-timing class outright; software AES would need bitslicing or masking to match, at more cycles and more code, for hardware benefit that does not exist on this part. Key schedule in uncached tightly-coupled memory. Derivation from a pre-shared root, sliding replay window on receive.
Zynq UltraScale+
CSU / A53
Now you have three implementations of the same primitive: the security unit's engine, the A53 cryptography extensions, and software. They differ in throughput, in who can reach the key, and in side-channel exposure. The engine is not automatically safe. Power and electromagnetic analysis target hardware engines specifically, which is why key rolling exists as a countermeasure in the first place. Choose by where the key must live, not by benchmark. A key that never leaves the security unit is worth more than throughput, and "the crypto is faster" is the wrong first sentence in a design review.

3.07 Faults, forensics, and verification

CWE-209
A fault is a security event. Capture the class and faulting address, zeroize keys, reset. Do not attempt to continue. A handler that dumps registers over a debug port in a fielded build is a memory-disclosure oracle an attacker triggers deliberately. Enable each fault class separately where the architecture allows it — letting everything escalate to a single catch-all throws away the classification that would have told you it was a protection violation.
DO-178C
Assurance vocabulary — levels A through E by failure-condition severity, with modified condition/decision coverage required at the top level. You are not certifying anything; you are expected to use the words correctly. The hardware equivalent for programmable logic is a separate standard, which matters the moment the fabric does something safety-relevant.
IEEE 12207
Bidirectional traceability — requirement to design to code to test and back. Every security requirement has at least one test that fails when it is violated. Orphan code and orphan tests are both findings. Threat model, then requirements derived from it, then tests, then code. A program audits the trace, not the cleverness.
Red team
Self-audit plan — coverage-guided fuzzing of the parser on a host build, a timing harness on tag comparison and key derivation, a glitch thought experiment against boot verification, and a zeroization audit. Every finding gets a weakness identifier and a regression test. Build the host-buildable seam now. A parser that only compiles for the target cannot be fuzzed later without a refactor.
Zynq UltraScale+ · added surface
Supply chain
A Linux build is a dependency graph you inherited. Generate a software bill of materials, track vulnerabilities against the kernel and every recipe, and have a patch story for fielded units before anyone asks. The bitstream is also an asset: encrypt and authenticate it, because unprotected programmable logic is a design-theft and a fault-injection surface at once.

3.08 Inter-processor communication

CWE-1189
Every IPC channel is a trust boundary — whether it crosses a radio link, a backplane, or two millimetres of silicon. The pattern is always shared memory plus a doorbell, and the failure is always the same: one side trusts the other because the same team wrote both. Validate on receipt regardless of who is nominally on the far end. No pointers in messages, no structs cast onto the buffer, bounded lengths, and a schema you can fuzz.
Zynq UltraScale+
OpenAMP
The framework to know by name, with the remote-processor lifecycle managed from Linux and message channels riding shared ring buffers signalled by inter-processor interrupts. Rings live in reserved memory that is uncached or explicitly maintained on both sides. Restrict which master may write which region and raise which doorbell in the interconnect firewalls. The channel is the boundary — protect it there, not in the message handler alone.

3.09 Process, clearance, export

Kanban
Surface the work as a board — backlog, threat modeled, in progress with a work-in-progress limit of one or two, in review, verified, done. A blocked column with the blocker named rather than implied. Definition of done for a security feature: requirement traced, a test that fails without the fix, static analysis clean, decision logged. Say "definition of done" out loud in a stand-up and it stops being vocabulary.
ITAR / EAR
Export control touches this work. Cryptographic implementations and encryption-capable hardware variants carry obligations; a personal radio project is not a defense article, but the habit of separating personal and program repositories is exactly what a facility security officer will ask about. Start the interim clearance application early. The timeline is months and it is frequently the gating item on an offer.

3.10 Interview drill — Sheet 3

  1. Walk me through your chain of trust. Where is the root and is it immutable? First-stage bootloader in write-protected flash, public key hash in one-time storage, signature over the application, rollback bits in one-way fuses. The root is software made practically immutable — weaker than a hardware ROM, and I can name what I would gain on a part that has one.Immutable ROM in the security unit authenticates the first-stage loader with a fused public key hash, locks the security resources, and hands the chain forward. Secondary keys are revocable by identifier so a signing key can rotate without bricking the fleet. That is a genuine hardware root, not a software approximation.Immutable first link holding a key or its hash in one-way storage, signature verification at every handoff, and a monotonic version check before control transfers.
  2. Why is a CRC insufficient for verifying an image? Unkeyed and linear — any modification is followed by a recomputation. Integrity against noise is not integrity against an adversary.
  3. The image is correctly signed and it is an old version with a known bug. What stops it? Nothing, without anti-rollback. A monotonic counter in storage the application cannot write, checked before handoff.
  4. Secure boot versus measured boot — when do you need both? Secure boot refuses locally; measured boot produces evidence a remote party can evaluate. You need both when someone off-device must decide whether to trust this unit — which on a fielded system is usually the actual requirement.
  5. Your boot ROM authenticates with RSA-4096 and cannot be changed. Is that CNSA 2.0 compliant? No — the suite requires quantum-resistant firmware signing and RSA is not. The layered answer: keep vendor secure boot on, encrypt and minimize the first stage, and have it verify all operational firmware with a post-quantum scheme before execution.
  6. Defend your authenticated-encryption choice with no accelerator available. A table-free construction removes the cache-timing class outright and fits the code budget; software AES would need bitslicing or masking to reach the same posture for no hardware benefit that exists on the part.
